**“이 코드는 어떤 순서로 실행되고, 어떤 상황에서 잘못될 수 있을까?”**

이 글에서는 검색창 코드를 따라 읽으며, 요청과 응답의 순서 때문에 생길 수 있는 문제를 정리한다. 아래 상황은 코드 흐름을 분석한 예시이며, 실제 API로 재현한 결과는 아니다.

## 상품 검색 컴포넌트

```tsx
import { useEffect, useState } from "react";

type Product = {
  id: number;
  name: string;
};

type Props = {
  searchProducts: (query: string) => Promise<Product[]>;
};

export function ProductSearch({ searchProducts }: Props) {
  const [query, setQuery] = useState("");
  const [products, setProducts] = useState<Product[]>([]);
  const [loading, setLoading] = useState(false);

  useEffect(() => {
    if (!query.trim()) {
      return;
    }

    setLoading(true);

    searchProducts(query).then((result) => {
      setProducts(result);
      setLoading(false);
    });
  }, [query, searchProducts]);

  return (
    <section>
      <label>
        상품 검색
        <input
          value={query}
          onChange={(event) => setQuery(event.target.value)}
        />
      </label>

      {loading && <p>검색 중...</p>}

      <ul>
        {products.map((product) => (
          <li key={product.id}>{product.name}</li>
        ))}
      </ul>
    </section>
  );
}
```

여기서 `searchProducts`는 검색어를 받아 상품 목록을 비동기로 반환하는 함수다. 부모 컴포넌트에서 전달되며, 이 예제에서는 함수의 참조가 안정적으로 유지된다고 가정한다.

코드 전체를 한꺼번에 이해하려고 하니 막막했다. 그래서 화면이 기억하는 값부터 살펴봤다.

## 화면이 기억하는 세 가지 값

```tsx
const [query, setQuery] = useState("");
const [products, setProducts] = useState<Product[]>([]);
const [loading, setLoading] = useState(false);
```

각 상태의 역할은 다음과 같다.

| 상태 | 의미 | 처음 값 |
|---|---|---|
| `query` | 사용자가 입력한 검색어 | 빈 문자열 |
| `products` | 화면에 표시할 상품 목록 | 빈 배열 |
| `loading` | 검색 요청을 기다리는지 여부 | `false` |

`useState`가 반환하는 첫 번째 값은 현재 상태이고, 두 번째 함수는 그 상태를 변경하는 데 사용한다.

예를 들어 `setQuery("사과")`를 호출하면 검색어 상태를 `"사과"`로 변경하도록 React에 요청한다. React는 변경된 상태를 바탕으로 화면을 다시 렌더링한다.

그렇다면 `setQuery`는 어디에서 호출될까?

## 사용자 입력에서 검색 요청까지

입력창에는 다음 코드가 있다.

```tsx
<input
  value={query}
  onChange={(event) => setQuery(event.target.value)}
/>
```

`value={query}`는 검색어 상태를 입력창에 표시한다.

사용자가 입력을 바꾸면 `onChange`가 실행된다. `event.target.value`는 입력창의 새 값이고, 이 값을 `setQuery`에 전달한다.

흐름을 간단히 적으면 다음과 같다.

```text
사용자가 입력한다
→ onChange가 실행된다
→ setQuery에 새 검색어를 전달한다
→ 검색어 상태가 바뀐다
→ 화면이 다시 렌더링된다
```

검색 요청은 `useEffect` 안에서 보낸다.

```tsx
useEffect(() => {
  if (!query.trim()) {
    return;
  }

  setLoading(true);

  searchProducts(query).then((result) => {
    setProducts(result);
    setLoading(false);
  });
}, [query, searchProducts]);
```

이 effect는 처음 실행될 때와 의존성인 `query` 또는 `searchProducts`가 바뀌었을 때 실행된다.

검색어가 빈 문자열이거나 공백뿐이면 요청하지 않는다. 검색어가 있다면 로딩 상태를 켜고 요청을 보낸다.

응답이 도착하면 상품 목록을 변경하고 로딩 상태를 끈다.

여기까지만 읽으면 자연스러운 코드처럼 보인다.

## 요청을 보내는 것과 응답을 받는 것은 다른 시점이다

내가 주의해서 봐야 했던 부분은 `.then()`이었다.

```tsx
searchProducts(query).then((result) => {
  setProducts(result);
  setLoading(false);
});
```

`searchProducts(query)`는 비동기 작업을 나타내는 Promise를 반환한다. 요청이 성공하면 `.then()`에 전달한 함수가 실행된다.

즉, 요청을 보낸 순간에 상품 목록이 바뀌는 것은 아니다. 응답이 올 때까지 기다렸다가 바뀐다.

그동안 사용자는 입력창을 계속 수정할 수 있다. 첫 번째 요청이 끝나기 전에 두 번째 요청을 보낼 수도 있다.

**그리고 먼저 보낸 요청이 반드시 먼저 완료되는 것은 아니다.**

## 검색을 연속으로 하면 어떤 일이 생길까?

사용자가 `사과`를 검색한 직후 `바나나`를 검색했다고 가정해보자.

실제 입력 과정에서는 더 많은 요청이 생길 수 있지만, 흐름을 이해하기 위해 두 요청만 생각해보겠다.

특히 한글은 조합 중에도 `onChange`가 발생하기 때문에, `사과`를 입력하는 동안 `ㅅ`, `사`, `삭`, `사과`처럼 여러 번 요청이 나갈 수 있다.

두 응답이 요청 순서대로 도착하면 문제가 드러나지 않을 수 있다. 하지만 `바나나` 응답이 먼저 도착하고, `사과` 응답이 나중에 도착하면 어떻게 될까?

| 순서 | 발생한 일 | 상품 목록 |
|---|---|---|
| 1 | `사과` 검색 요청을 보낸다 | 기존 목록 |
| 2 | `바나나` 검색 요청을 보낸다 | 기존 목록 |
| 3 | `바나나` 응답이 도착한다 | 바나나 상품 |
| 4 | `사과` 응답이 도착한다 | 사과 상품 |

마지막 순간에는 입력창에 `바나나`가 적혀 있는데, 상품 목록은 `사과` 검색 결과가 된다.

사용자가 마지막으로 검색한 것은 바나나지만, 화면에는 마지막으로 **도착한 응답**이 반영된 것이다.

이처럼 비동기 작업이 완료되는 순서에 따라 결과가 달라지는 문제를 경쟁 상태, 또는 race condition이라고 부른다.

## 원인은 어느 줄에 있을까?

문제를 일으키는 핵심 부분은 다음 줄이다.

```tsx
setProducts(result);
```

이 코드 자체가 항상 잘못된 것은 아니다. 문제는 **응답을 반영하기 전에 확인하는 조건이 없다는 것**이다.

현재 코드가 하는 일은 다음과 같다.

```text
응답이 도착했다
→ 그 결과로 상품 목록을 교체한다
```

하지만 검색창이 원하는 동작에는 한 단계가 더 필요하다.

```text
응답이 도착했다
→ 현재 유효한 검색 요청의 응답인지 확인한다
→ 유효할 때만 상품 목록을 교체한다
```

각 요청의 `.then()`은 자신의 응답을 받으면 실행된다. 그사이에 검색어가 바뀌었다는 이유만으로 이전 요청의 콜백이 자동으로 무효화되지는 않는다.

따라서 이전 요청의 응답도 나중에 `setProducts`를 호출할 수 있다.

## 같은 방식으로 다른 상황도 살펴보기

응답 순서를 생각하기 시작하니 다른 질문도 생겼다.

### 검색 중에 입력을 모두 지우면?

현재 코드는 검색어가 비어 있으면 바로 반환한다.

```tsx
if (!query.trim()) {
  return;
}
```

새로운 요청은 보내지 않지만, 기존 상품 목록을 비우지는 않는다. 이미 진행 중인 요청도 무효화하지 않는다.

따라서 입력창을 비운 뒤에도 이전 상품 목록이 남거나, 늦게 도착한 응답으로 목록이 다시 채워질 수 있다.

“빈 검색어에는 요청하지 않는다”와 “빈 검색어일 때 화면을 비운다”는 별개의 동작이었다.

### 요청이 실패하면?

현재 코드에는 성공했을 때의 처리만 있다.

```tsx
searchProducts(query).then((result) => {
  setProducts(result);
  setLoading(false);
});
```

요청이 실패하면 이 성공 콜백은 실행되지 않는다. 따라서 이 코드에는 실패한 요청의 로딩 상태를 종료하거나 오류를 표시하는 처리가 없다.

그래서 요청이 실패하면 `loading`이 `true`로 남아 "검색 중..." 문구가 계속 표시된다. 처리되지 않은 Promise rejection도 발생한다.

### 요청이 여러 개 진행 중이면?

요청마다 응답이 도착할 때 다음 코드를 실행한다.

```tsx
setLoading(false);
```

이전 요청이 먼저 끝나면 최신 요청이 진행 중이어도 로딩 표시가 꺼질 수 있다.

상품 목록뿐 아니라 로딩 상태도 **어느 요청을 기준으로 갱신할 것인지** 정해야 한다는 뜻이다.

## 해결 코드를 작성하기 전에 정할 것

이 단계에서 곧바로 코드를 바꾸기보다, 이 검색창이 지킬 규칙부터 정해봤다.

- 최신 검색 요청의 결과만 화면에 반영한다.
- 검색어가 비어 있으면 결과를 비운다.
- 새 검색을 기다리는 동안 이전 결과를 숨긴다.
- 요청 실패 시 오류를 표시하고 로딩을 종료한다.
- 이전 요청의 성공이나 실패가 최신 검색 상태를 바꾸지 못하게 한다.

구현할 때는 이전 effect의 요청을 무효한 것으로 표시하거나, 요청마다 번호를 붙여 최신 요청인지 확인하는 방법을 생각해볼 수 있다.

요청 함수가 취소 기능을 제공한다면 이전 요청을 취소하는 방법도 검토할 수 있다. 다만 이 예제의 `searchProducts`에는 취소 기능이 없으므로, 응답을 받더라도 화면에 반영하지 않는 처리가 필요하다.

이번 글에서는 해결 코드까지 다루기보다, 어떤 조건이 빠져 있는지 이해하는 데 집중했다.

## 코드를 읽을 때 시작할 세 가지 질문

처음에는 코드의 모든 문법과 구조를 한 번에 이해하려고 했다. 하지만 사용자 행동 하나를 정하고 흐름을 따라가니 살펴볼 범위가 줄었다.

앞으로는 다음 질문부터 시작하려고 한다.

1. **사용자가 행동하면 어떤 함수가 실행되는가?**
2. **그 함수는 어떤 상태를 변경하는가?**
3. **변경된 상태는 화면 어디에 사용되는가?**

비동기 작업이 있다면 두 가지 질문을 더한다.

- 이 작업을 기다리는 동안 사용자가 다른 행동을 하면 어떻게 되는가?
- 이전 작업이 나중에 완료되어도 현재 화면을 바꿔도 되는가?

이 검색창에서는 두 번째 질문이 문제를 찾는 단서가 됐다.

## AI의 도움을 받는 방법도 바꿔보기

AI에게 바로 수정 코드를 요청하면 해결된 결과를 빠르게 얻을 수 있다. 하지만 내가 왜 문제가 생겼는지 설명하지 못하면, 비슷한 코드를 다시 만났을 때도 같은 부분에서 막힐 수 있다.

그래서 학습할 때는 다음처럼 요청해보려고 한다.

> 수정 코드를 바로 주지 말고, 사용자가 입력했을 때 실행되는 순서를 설명해줘. 특히 요청을 보낸 시점과 응답을 받은 시점을 구분해줘. 내가 흐름을 설명해본 뒤 빠진 부분을 짚어줘.

답변을 읽은 뒤에는 코드를 덮고 내 말로 설명해본다.

“사과 요청이 늦게 도착하면 왜 바나나 결과를 덮어쓰는가?”

이 질문에 답할 수 있는지가 이번 학습의 첫 번째 기준이다.

## 다음에 확인할 것

이번에 알게 된 것은 검색 결과가 한 번 정상적으로 표시됐다는 사실만으로, 모든 상황에서 올바르게 동작한다고 판단할 수는 없다는 점이다.

다음에는 응답 시간을 조절할 수 있는 가짜 검색 함수를 만들어서 다음 상황을 직접 재현해보려고 한다.

- 이전 검색 응답이 최신 검색 응답보다 늦게 도착하는 경우
- 검색 도중 입력을 모두 지우는 경우
- 요청이 실패한 뒤 다시 검색하는 경우

그다음 이전 응답을 무시하는 처리를 추가하고, 같은 상황에서 화면이 어떻게 달라지는지 비교할 것이다.

지금은 문제를 해결하는 코드보다 먼저, **문제가 발생하는 순서를 설명할 수 있게 된 것**을 첫 단계로 삼으려 한다.
